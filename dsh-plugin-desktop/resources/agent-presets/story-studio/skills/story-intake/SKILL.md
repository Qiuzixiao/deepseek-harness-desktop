# Story Intake

在开始立项、选题、人物设定、大纲、分集、章节或参考拆解前使用本技能。目标是让工作尽快推进，不是完成一张固定需求表。

## 1. 先判断输入是什么

区分以下三类内容：

- **真实创作需求**：用户明确要求当前处理、生成或修改的作品。
- **说明性例子**：用户用于解释希望 Agent 如何工作的样例。除非用户明确确认，不得把样例自动建立成项目。
- **参考材料**：对标剧本、小说、提案、表格或其他来源文件。它们是分析输入，不是新作品事实。

同时确认本轮交付，例如选题整理、人物设定、爽感结构、季纲、分集纲、正文、改写、审校或参考拆解。用户已经说清时不要重复询问。

## 2. 建立需求账本

从用户输入和已读取文件中整理：

| 类别 | 内容 |
| --- | --- |
| 作品形态 | 短剧、小说、跨媒介或尚未决定 |
| 本轮交付 | 用户现在要拿到什么 |
| 规模边界 | 季/集、卷/章、单集或章节长度、当前只做到哪里 |
| 受众与渠道 | 年龄、性别、下沉程度、平台或阅读场景 |
| 题材与基调 | 类型、时代、地域、情绪体验、尺度 |
| 核心故事 | 主角、目标、阻力、核心机制、差异化 |
| 创作约束 | 必须保留、禁止内容、格式、截止范围 |
| 参考材料 | 文件路径、用途、允许借鉴的层级 |

每项标记为：`confirmed`、`assumption`、`open` 或 `conflict`。不要为了填满表格而提问。梳理核心故事/核心机制时，可用 grep 按关键词检索 `灵感速记/灵感速记.md`（若存在），命中则评估是否并入账本，未命中不阻塞。

## 3. 决定是否询问

只有满足下列任一条件时才询问：

- 无法判断用户要短剧、小说还是仅做方向讨论，并且形态会改变本轮输出；
- 集数、季范围、卷章规模或交付范围互相冲突；
- 缺少目标受众/渠道会直接改变题材表达、节奏或尺度；
- 核心机制的限制、结局方向或必须保留项存在两种不可兼容解释；
- 参考材料的用途不清楚，无法判断要总结、拆解、改写还是仅作风格参照。

一次最多三个问题，并说明每个问题会影响什么。能通过合理假设推进的姓名、地点、普通配角、细节数字和措辞不阻塞工作。

## 4. 直接产出

若信息足够，直接完成用户本轮要的内容。若用户要建立长期作品，加载 `story-project` 并把需求账本写入 `项目说明.md`；若只是一次方向讨论，不要擅自创建目录。

结果中清楚区分：

- 已确认内容；
- 本轮采用的假设；
- 尚未决定但不阻塞当前工作的事项；
- 已发现的冲突；
- 本轮交付物和保存位置。

参考材料分析必须记录来源路径，并把“原材料事实”“分析结论”“可迁移方法”“新作品表达”分开。
