# 短剧创作 Agent 内核重构设计

> 文档类型：架构设计参考
> 目标：把短剧 Agent 从"长篇提示词 + 原子状态机"重构为"开放 agent 循环 + 场级领域工具 + 可检索可覆盖的方法论知识层"，核心任务为垂直文学创作，交互范式对标 Claude Code / Codex，但为创作域重做反馈回路。

## 0. 问题诊断（现状）

现有 `screenplay-v1` 只挂载两个插件：`screenplay-agent` 与 `tool-ask-user`。其余全部 Harness 能力（plan-mode、todo、subagent、fs/search、skill、goal、compaction、workflow）均未启用。工具白名单裁剪到 17 个 `screenplay_*` 领域工具加 `ask_user_question`；控制流以约 270 行系统提示词手写实现；方法论 M1–M7 烧死在提示词末尾；领域工具为"整文件快照式"原子提交。

由此得到三个结构性缺陷：

1. **模型被绑成执行器，不是 agent。** 每集只有一次"生成—校验—落盘"机会，没有"读回自己的草稿 → 发现缺陷 → 定点修改 → 再校验"的迭代闭环。agent 感（走一步→看结果→调整→再走）不存在。
2. **控制流在提示词里。** 状态机不在代码中而在文本块里，不可检索、不可覆盖、不可演进；迭代需改代码并重新发布。
3. **信道 B（创作判断）没有反馈机制。** 只有客观校验（信道 A），没有"这个钩子够不够劲"这类的判断反馈，模型永远不知道"写得好不好"。

## 1. 设计原则：地基 / 创作面 / 连接件

现有一轮定案的统摄性原则。它解释本设计为什么按下文方式拆分：**系统把"必须为真"的东西搭结实，把"由人选择"的东西留全给用户；工具是二者之间的连接件，而连接件怎么设计，决定了用户创造的难易。**

类比创作工具（DAW / 编辑器）的铁律：采样率、音符时序、路由是确定性的，系统硬管；你做什么声音、什么和弦是自由的；决定"玩家创造门槛"的，是工具能否方便地开一个 synth、拧一个滤波器、随时撤销、反复试。

### 地基（系统硬保证，代码拥有）

"必须为真"的不变式，全部落地为代码里的硬校验，**不交给模型、不交给用户、不交给提示词**：

| 不变式 | 代码保证 |
|---|---|
| 项目身份 | 每会话唯一绑定项目；名 = 文件夹名；过程不可改名 |
| 版本化 | revision 单调递增；每次写入为原子版本提交；并发冲突（revision 不符）不静默覆盖 |
| 阶段排序 | Intake→合同→大纲→分集→正文→交付；不可跳阶段；状态机门控 |
| 集数序列 | 严格按序；nextEpisode 由状态推导，不由模型挑；不可跳集、不可预写 |
| 结构有效 | 标题/场次/人物行/动作行/闪回成对/卡点/集尾由校验器保证；字数区间对应时长档 |
| 连续性硬检查 | 角色状态/关系/伏笔/未闭合悬念，跨集矛盾与提前泄露被检出 |
| 交付 | 只合并完整、校验过的正文；正式文件，非草稿 |
| 修改安全 | save/discard 是明确用户边界；pending change 先暂存，用户显式"保存修改"才应用 |

**这些是地基，与创作权无关。** 用户在台上自由演，但不能拆舞台——否则状态机、版本、交付全崩。

### 创作面（创作权，用户/编导）

台上怎么演（钩子、反转、节奏、人物走向、文风、选哪个方案），**全部由用户/编导决定**。系统是懂行的编辑 + 智囊：提方案、分析、选项、挑刺，不拍板（见 §3 信道 B）。

### 连接件（工具层，决定"创造门槛"）

区分两种工具：

- **管道（现状）**：`create_episode(content)` —— 给你一整集，校验，写。要么过要么不过，一锤子买卖。"封闭式"：它包着用户，用户只能往一个筒里倒。
- **积木（目标）**：`write_scene(ep, sceneNo, content)` —— 给你一个小轴，你操作它，系统在边界校验。"连接式"：用户拿着它拼。

积木的四条设计规则（直接决定用户创造门槛高低）：

1. **可读性** —— 每个 read 给用户"创造所需的信息"（我在哪、有什么、已定了什么）。见 §8 `read_project_context` / `read_artifact` / `search_project`。
2. **地基内自由** —— write 侧只校验结构/格式（信道 A），**从不校验风格**。这是"地基结实 + 创作面自由"的直接体现：用户怎么写都行，只要结构有效、与项目状态一致。
3. **可挽回** —— 反复迭代，校验便宜、结果可读；不做"一次成型、不过就整集重来"的烧钱（即现状 `create_episode` 的缺陷）。
4. **决策上抛** —— 遇到真正的创作分叉，工具/模型给出选项，用户挑；系统不偷偷替用户选。

### 工具层是"agent 和人共用的一套积木"

工具层**不假设是谁在操作**。它同时支持两条路径：

- **模型驱动**：用户说"写第 4 集"，agent 作为"熟练编辑"用同一套积木工具把活干了，把方案和透镜意见呈上来。
- **人直接操作**：用户想自己改第 3 场、自己读一遍第 N 集、自己看校验结果、自己挑一个开场方案——工具层要**结构化、可预期、可撤销**，让人也能握得住。

这样，模型是"替你操作的高级编辑"，但用户对成品永远有**直接把手**。这就是把"创造力留给用户"落到工程上的做法。

**一句话总结**：地基是舞台，模型是舞台监督，用户和编导是导演与演员。舞台监督把灯位、轨道、校验关（A）搭好并把每一场能不能演过守好，但戏怎么演、哪场怎么走，是导演和演员的事。

## 2. 架构目标形态

三件东西塑造模型行为，而非一份脚本：

| 层 | 内容 | 职责 |
|---|---|---|
| **① Agent 大脑**（开放的循环） | `agent-loop` + plan-mode + todo + 透镜 subagent + skill | 负责推理、分解、规划、走步、观察、修正 |
| **② 领域工具**（细粒度、可迭代、可校验） | 场的读写 + 校验（A）+ 自检清单（B）+ 提交 | 负责"走路"：让模型围绕制品以小步迭代 |
| **③ 知识层**（方法论 skill/references） | `SKILL.md` 路由 + 按阶段 references | 负责"判断"：提供方法参考，作为信道 B 的原料 |

三个层全部挂在一个**项目内 workspace 作用域**上：模型能读、能搜、能改的只有它当前绑定的项目目录。

贯穿上述三层的第四要素是 **④ 文风学习闭环**（见 §7）：把用户/编导的创作行为沉淀为可复用的文风档案，使系统越用越贴合团队口味。它不是独立的一层，而是"如何让①②③随时间变得更懂用户"的机制。

## 3. 核心概念：信道 A 与信道 B

文学创作没有"编译通过"这道客观关卡。必须把"什么算对"拆成两条可靠程度不同的信道：

### 信道 A —— 可机械校验的事（相当于代码的"测试"）
- 格式与结构：标题、场次、人物行、动作行、`【卡点特写】`/`【本集完】`标记、闪回成对 `【闪回】…【闪回结束】`
- 连续性：角色状态、关系、道具、伏笔、未闭合悬念，跨集不矛盾、不提前泄露
- 集纲六字段齐全、集数连续、标题用项目名、总集数正确
- 状态机：revision、集数推进、save/discard 边界、交付合并

**A 项是硬门（hard gate）**：不过不放行。代码能判绝对对错，让模型能确定地修正。这是它"能自主"的地基。

### 信道 B —— 需要判断力的事（创作的主战场）
- 钩子是否确立主角主动目标、反转是"真反转"还是"假反转"、节奏拖/赶、人物成长线是否兑现、台词是否在人物知情范围

**B 项是软门（soft gate），且创作权在用户 —— 不是模型。**
系统在信道 B 中的角色是**懂行的编辑**，不是创作的掌管者：它提出有依据的方案、分析、选项、挑刺，但**最终拍板的是用户和编导**。方法论在信道 B 的作用不是"约束用户按它写"，而是"让系统有足够的行业判断力，能给出真正内行、有价值的建议和可选的创作空间"。

创作权归属（本轮定案的核心修正）：

| 范畴 | 谁说了算 | 系统角色 |
|---|---|---|
| 基础的东西（格式、状态机、版本、集数推进、连续性硬矛盾、交付规则、save/discard） | 系统硬守（代码） | 守门员，不可被创作权覆盖 |
| 创作的东西（钩子、反转、节奏、人物走向、文风） | 用户 / 编导 | 懂行的编辑：提方案 / 分析 / 选项 / 挑战，不拍板 |

### 边界规则（防机械化的护城河）
- **装"对错"，不装"好坏"。** 若把 B 项硬塞进代码规则，会得到一个"强制模型按算法写剧情"的编译器 → 模型为过审写出套路化文本，杀死文风。
- **A 信道校验器少而准。** 只拦真正不可接受的（格式 / 字数 / 连续性硬矛盾），不对艺术表达吹毛求疵。校验器是守门员，不是编辑。

## 4. 编辑单元：场

现状为"整文件快照式"：`screenplay_create_episode` 一口气灌整集，无回头、无定点修正。

重构采用折中：

- **写 / 改**：按**场**进行。`write_scene(集, 场, 内容)` 只改某一场，写作时顺带读到前后场，保持文风与承接。
- **审 / 提交**：按**整集**进行。写完后 `validate_episode(集)` 做整集级信道 A 校验，`diagnose_episode(集)` 做信道 B 自检清单 + 透镜 subagent 审阅，全过或综合判断后 `commit_episode(集)` 落盘正式文件。

**为什么这样折中**：碎片化到每场独立写会丢文风（写到第 3 场忘了第 1 场的人设语气），所以"写"允许读前后场；但"审"和"提交"回到整集粒度，保证整体一致性。这既给了模型迭代空间，又不牺牲文风连贯。

## 5. Agent 大脑的用法（区别于 coding 域的映射）

| Harness 原语 | coding 域用法 | 短剧创作域用法 |
|---|---|---|
| **todo** | 任务清单，完成=测试绿 | 多步创作骨架：立项→合同/设定/角色→大纲→分集→每集写作+校验。完成标准为"校验过 + 本阶段方法论自检过 + 用户认可"，要在描述中写清 |
| **plan-mode** | 探索 repo → 出方案 → 批准 → 实施 | 承接"讨论方向 → 确认 → 建文件"。状态机从"死的提示词步骤"变成"模型的规划行为" |
| **subagent（透镜批评者）** | 子 agent 做验证 / 并行开发 | **只做审查，不并行生成**：节奏 / 人物压力成长 / 钩子悬念反转卡点 / 跨集连续性 各一个视角，主 agent 汇总。避免正文并行导致风格漂移；兼作上下文隔离（主 agent 不必塞满 12 集正文） |
| **skill** | 按需加载文档 | 方法论按阶段加载，见 §6 |

**subagent 的角色定为"透镜批评者"**：读某集（或某评估对象）按各自视角给评判，**面向用户/编导呈现**，主 agent 汇总。不做并行正文生成。

透镜视角采用**多维口径**：
- **编剧口径**：人物压力、成长线、对白潜台词、四幕结构——关注"故事对不对"
- **编导口径**：节奏、画面、镜头感、商业性、卡点可拍性——关注"拍出来好不好看"

同一段内容，从编剧看和从编导看结论可能不同。系统分别呈现，供用户/编导作为挑选取舍的依据。透镜 subagent 是"给团队的智囊"，不是模型内部自行消化的判断。

## 6. 方法论知识层（skill/references）

现状 M1–M7 烧死在 `prompt.ts` 末尾（约 40 行）。重构移出为可检索、可覆盖的 skill。

### 结构
```
short-drama-zenwit/
├── SKILL.md            # 适用场景、核心原则、任务→reference 路由、事实边界
└── references/
    ├── m1-creative-spark.md      # 创意五元组（Intake 讨论）
    ├── m2-four-act-beats.md      # 四幕二十拍（大纲讨论）
    ├── m3-hooks-suspense-reversal.md  # 钩子/悬念/反转/卡点（集纲字段）
    ├── m4-character-pressure.md  # 人物压力与成长（角色讨论+模板校验）
    ├── m5-scene-dialogue-visual.md    # 单场与对白视听化（正文）
    ├── m6-revision-checklist.md  # 70 项清单（修改/诊断）
    └── m7-delivery.md            # 平台交付与商业准备
```

### 关键原则
1. **每次会话先加载 `SKILL.md` 本身**（很短，只讲适用场景与路由），落到具体阶段再按需加载对应 reference。即使路由判断出错，模型手里也握有"该去哪找"的地图。
2. **方法论是"方法参考"，不是"项目事实"。** 技能可被用户覆盖（project / user 作用域同名覆盖），但项目事实（角色/时间线/剧情定论/集数/交付规则）只由领域工具 + 正式文件保证，技能无论怎么覆盖都动不了它。
3. **方法论是"心智模型"，不是"模板指令"。** 区分标准：读完后模型是"套结构模板"（提示词工程）还是"应用方法做判断"（知识）。写 `references` 时给"如何判断"而不给"必须这样写"。

## 7. 文风学习闭环（越用越好）

**核心思路**：用户的写作行为里，编码了一份反映其个人风格（含编导团队口味）的资产。系统的目标是把这些行为痕迹精准提炼为可复用、可覆盖、可随使用增长的"文风档案"，而非让用户手动配置或让系统凭空推断。

用户是团队（编剧 + 编导），创作权与最终拍板在用户手里，因此**用户认可/留下的正式文件能真实反映团队想要的样子**，这是文风样本可用的前提。

### 文风资产三个来源（由强到弱）

1. **工作产物（最有力、最隐式）**：用户认可、亲手改过、整集放行的正式剧本即文风正样本。每写完整一集（编剧 + 编导点头放行），即以该整集作为一部完整的团队认可样例，**增量并入**文风样本库。
2. **改写行为（次强、对话捕获）**：用户说"这里改成…"或直接重写句子——这是最明确、最直接的文风反馈。收集"用户亲自署名改过的 diff"作为高价值样本，不当作一次性修改丢弃。
3. **方案选择（弱、处处有）**：用户从 2–3 个开场/走向方案中挑了一个——挑中的即偏好信号。信号弱，只保留结构性主题（钩子类型、冲突类型），不细挖。

### 落地流程（后台隐式收集 + 到量主动提议 + 用户确认）

```
用户在创作中（写/改/认可） → 系统后台积累文风正样本（不打断创作）
        ↓ 达到触发量（如 ≥5 整集 或 ≥10 处明确改写）
模型主动提议：我观察到你的偏好倾向如此，是否提炼成一份"我的文风档案"？
        ↓ 用户确认 → 生成 references/style-profile.md（可编辑、可覆盖、可删除）
        ↓ 以后每集：模型加载 这份文风档案 + 按需的方法论 reference
```

三要素齐了：**不打断创作（隐式收集）→ 到量主动提议（触发、用户知情）→ 可覆盖可回退（不锁死）。**

### 作用域分层

- **全局风格（跨项目，user 级）**：这个人/团队的稳定写法偏好，随人走，不锁死在一个剧本上。
- **项目风格（单项目，project 级）**：只对当前剧成立的语调/设定，随项目走。

### 文风档案 vs 方法论 skill vs 项目事实

| 层 | 内容 | 来源 | 可覆盖性 |
|---|---|---|---|
| 方法论 skill（`short-drama-zenwit`） | 行业通用创作规律（钩子/压爽/四幕） | 用户提供 / 行业知识 | 可被用户方法覆盖 |
| 文风档案 skill（`short-drama-style`，user/project 级） | 这个团队自己的写法偏好 | 用户行为轨迹提炼 | 用户主动生成、可编辑 |
| 项目事实（合同/设定/角色/时间线） | 本项目定论 | 用户 + 领域工具 | 不可覆盖（结构硬约束） |

文风档案与项目事实同为团队专属，但**文风可演进（越用越准）**，项目事实固定（一项目一定论）。

### 碰撞优先级

用户明确指定的写法 > 本项目已定/已验证的写法 > 用户历史提炼的文风 > 行业方法论（默认）。

### 防"锁死"的纪律

文风档案是**参考**，不是**必须遵守**。若写成"你必须这样写"的模板，就又沦为提示词工程，且会把用户锁死在套路上——风格是"贴近用户的审美"，不是"重复用户过去的每一处偏好"。留样本、可覆盖、以团队拍板为准，才能既随使用增长又不僵化。

## 8. 领域工具清单（目标形态）

围绕"场"重做，替代现有整文件快照式工具：

```
read_project_context()        # 紧凑状态投影（phase/revision/进度）
read_artifact(path)           # 按需读某个正式文件（合同/设定/角色X/大纲/集纲/第N集）
search_project(query)         # 只在项目内 grep（找角色名/伏笔/跨集引用）
write_scene(ep, sceneNo, c)   # 只写/改某一场——写作的"diff"，写作时可见前后场
validate_episode(ep)          # 信道 A：结构+连续性+时长/字数，返回字段级问题
diagnose_episode(ep)          # 信道 B：70 项清单的判断项，返回带视角的检查点
commit_episode(ep)            # 校验+自检全过或综合判断通过后落盘正式文件
# 保留于领域层（状态机/交付，不得由模型自由发挥）：
#   project 绑定、revision/operationId 乐观并发、save/discard 确认边界、
#   screenplay_merge_delivery 交付合并、version 恢复
```

**迭代闭环**：`read next-episode outline → read episode N-1 → write scene1 → validate → 修 scene3 → validate → diagnose → 修节奏 → commit`。每步有反馈，模型真正在"写"，而非执行写好的管道。草稿不落磁盘文件（维持现状"不允许讨论稿文件"），只在模型推理循环内迭代。

## 9. 反馈回路总览

```
┌──────────────── 模型（agent-loop） ────────────────┐
│  走步：写一场 → 观察：校验A → 修正 → 校验A → 自检B → 给方案 │
└──────────────┬─────────────────────────────────────┘
               │ 信道A（硬门，代码校验，系统硬守）
               ▼
      ┌──── 结构 / 连续性 / 字数 ────┐  不过 → 回模型修正
      └──────────┬────────────────┘  过
                 ▼
      ┌──── 信道B（软门，创作权在用户）───┐
      │ ① 模型给方案/分析/选项/挑刺        │
      │ ② 透镜 subagent 给多视角意见       │ 用户/编导拍板
      │ ③ 用户/编导挑取 + 重大分叉介入      │
      └──────────┬─────────────────────┘
                 ▼
       commit_episode → 正式文件落盘
```

**A 硬拦、B 引导**：A 用代码硬守客观稳定的值；B 用模型（懂行编辑）+ 透镜 subagent（智囊）给足信息，最终创作拍板权在用户/编导。

## 10. 与既有交付纪律的兼容

- 正式文件仍是版本化的（revision / operationId / snapshot / stableId），状态机推动，`commit_episode` 才落盘正式产物。
- 无散落"讨论稿/草稿/审批稿"文件——迭代发生在模型循环内，不落到磁盘。
- `screenplay_merge_delivery`、版本恢复、save/discard 确认始终在领域层（代码），skill / B 信道不得绕过。
- 兼容模式（未选 `screenplay-v1`）默认客户端行为不变。

## 11. 分期落地

### 阶段 1：放开作用域 + 接入 skill / todo
- 给 `screenplay-v1` 挂 `skill-filesystem` + `tool-skill` + `tool-todo`，将 `skill`、`todo` 加入白名单。
- 把 M1–M7 从 `prompt.ts` 移出，建 `short-drama-zenwit` skill（`SKILL.md` + 按阶段 references）。
- `prompt.ts` 清空到只剩：角色、项目状态边界、Skill 使用规则。
- **验证**：已有 SkillRegistry / tool-skill / 短剧测试通过；`short-drama-zenwit` 可发现；命中任务按需加载。

### 阶段 2：领域工具场级化（核心，改动最大）
- 把整文件快照式 `screenplay_*` 拆成 §8 的场级读写 + 校验 + 提交。
- `validate_episode` 落地为信道 A 硬门；`diagnose_episode` 落地为信道 B 自检清单。
- 让模型在"写一集"粒度上获得多次迭代机会（读回自己的产出 → 对照 → 修 → 验 → 落盘）。
- **验证**：写一集时模型能读回、发现 A 项错误并定点修正；`git diff --check`、Markdown 链接检查、相关类型检查、短剧测试通过。

### 阶段 3：todo + plan-mode + 透镜 subagent（可选，收益最大）
- 开启 `plan-mode`（承接"讨论→确认→建文件"的规划行为）。
- 开启 todo（多集写作为任务驱动推进）。
- 挂透镜 subagent：编剧口径（节奏 / 人物压力 / 钩子反转 / 跨集连续性）+ 编导口径（节奏 / 画面 / 可拍性），主 agent 汇总，面向用户/编导呈现。
- **验证**：写多集时用 todo 驱动；提交前透镜 subagent 给出多视角评价供团队挑选；不并行生成正文。

### 阶段 4：文风学习闭环（越用越好）
- 在创作行为中后台收集文风正样本（认可/改写的正式文件）。
- 到达量后主动提议，用户确认后生成 `references/style-profile.md`（user/project 级）。
- 新集自动加载文风档案 + 按需方法论 reference；可编辑、可覆盖、可删除。
- **验证**：完成几集后能提炼出稳定偏好；用户确认后新集写作体现该偏好；文风档案可被用户覆盖或回退。

## 12. 未决 / 需用户拍板

### 已拍板（本轮定案）

1. **场作为编辑单元**：写/改按场、审/提交按整集的折中。工具改动最大，是 agent 感的关键。
2. **subagent 角色**：仅"透镜批评者"，不并行生成正文；采用**多维口径**——编剧口径（故事对不对）+ 编导口径（拍出来好不好看），分别呈现供团队挑选。
3. **用户参与度**：模型自主决定基础项（信道 A），创作权在用户/编导；**只在"重大创作分叉"时请人**（剧情大转折、人设推翻、ending 方向、跨阶段方向变化），其余模型给足方案、用户挑，不强求逐条确认。
4. **信道 B 自检**：模型落盘前主动自审、给方案/分析/选项/挑刺，**但最终拍板的是用户/编导**（创作权归还用户）。
5. **方法论 skill/references**：按阶段按需加载、可被用户覆盖；方法论是方法参考非项目事实。
6. **信道 A/B 拆分**：装对错不装好坏；A 硬门 B 引导；A 校验器少而准。
7. **文风学习闭环**：跨项目文风放 user 级、单项目放 project 级；后台隐式收集 + 到量主动提议 + 用户确认；以"一整集被认可"为提炼节奏；可覆盖、可回退。

- 编导口径是否作为独立 subagent 视角纳入 MVP，还是先只做"用户 + 一个懂行编辑"的最小闭环。
