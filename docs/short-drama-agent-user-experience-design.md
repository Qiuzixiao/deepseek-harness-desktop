# 短剧 Agent 用户体验与能力组合设计（历史方案）

> 本文记录短剧 Agent 面向创作者的目标体验。它补充内核架构文档，重点回答“用户怎么自然创作、Agent 如何在后台配合、Skill 和 Agent 如何被复用”。本文不把任何一套编剧资料认证为唯一正确的方法。
>
> **实现状态说明（2026-09）**：本文整体是历史产品探索，不是当前运行契约。当前没有 `write_episode`、草稿/正式提交、领域校验、版本或固定项目对象；普通文件通过 `read/write/edit/move/delete` 直接处理。当前实现见 `dsh-short-drama/README.md`。

## 1. 结论先行

短剧 Agent 应该是一个**面向创作意图的工作区 Agent**，而不是要求编导操控文件和工具的项目表单。

用户只需要表达：想写什么、想怎么改、哪些地方不满意、这次想尝试哪个方向。Agent 负责观察工作区、理解已有内容、组织文件、调用短剧能力、提出方案和保存版本。

建议采用以下产品模型：

```text
用户工作区       用户自由放置和组织创作资料
项目识别层       记录哪些内容承担人物、大纲、正文等作用
领域能力层       提供短剧/小说对应的创作工具和客观校验
Skill 知识层      提供可选写法、工作流、知识和审查视角
Agent 配置层      组合领域、工具、Skill 和交互偏好
```

核心原则是：

- 用户拥有创作方向和最终决定权；
- 用户可以自由组织创作资料和选择工作方式；
- Skill 提供参考，不直接控制目录、权限或正式提交；
- Agent 自动处理常规操作，不把内部工具调用变成用户的工作负担；
- 系统只强制保护项目安全、版本、草稿/正式文件和必要的客观校验。

## 2. 用户真正面对的是什么

用户不应该看到这样的工作要求：

> 先创建人物文件，再调用大纲工具，然后写第 1 集第 1 场。

用户应该可以这样说：

> 我想写一个都市情感短剧，女主发现丈夫隐瞒了一个重大秘密。先帮我想三个不俗套的开场。

Agent 在后台自行判断：

- 当前项目是否已经有设定和人物；
- 哪些文件与这次任务有关；
- 应该先给方案，还是直接写草稿；
- 哪些内容需要用户选择；
- 结果应该保存为草稿，还是提交为正式版本。

文件、目录、Skill 和工具是工作台内部的组成部分，不应成为创作者必须学习的操作语言。

## 3. 真实使用场景

### 场景一：从一个模糊想法开始

用户：

> 我想写一个被背叛后反击的短剧，但不想做成常见的爽文套路。

Agent：

> 可以从三种开局方向展开：
> 1. 观众先知道真相，女主暂时不知道；
> 2. 女主先发现异常，但证据指向错误的人；
> 3. 女主表面被动，实际在利用对方的误判。
> 你更想让观众先同情她、怀疑她，还是期待她反击？

用户选择方向后，Agent 开始写开场或继续追问一个真正影响剧情的问题。用户不需要决定先建哪个文件。

### 场景二：在已有项目中继续创作

用户打开一个自己整理过的工作区，里面可能有任意名称的文件：人物笔记、故事大纲、正文、参考资料等。

用户：

> 接着上一集写，女主已经知道丈夫在撒谎，但不能马上揭穿。

Agent：

> 我已找到前两集正文和人物设定。上一集结尾留下了“账本被调包”的线索。我会保持女主暂不揭穿，先写她如何验证这个线索。

如果文件含义不确定，Agent 只需要一次性说明识别结果并请求确认，不要求用户重新整理目录。确认后的对应关系可以被项目记住。

### 场景三：用户改变创作流程

用户：

> 我不想先写完整大纲，我想先把几个关键场景写出来，再反推故事线。

Agent 可以按照这个流程工作，并提醒影响：

> 可以。这样更适合探索人物和场面，但完整因果链会晚一些确定。我会先把关键场景作为草稿保存，并在后续提醒可能出现的连续性问题。

缺少某个可选文件不能自动变成“无法继续”。只有用户选择的工作方式确实会导致事实无法判断时，Agent 才提问。

### 场景四：使用用户自己的写法

用户：

> 以后写短剧时参考我的写法：台词短一点，少解释，多用人物之间的潜台词。

Agent 可以在当前项目或指定 Agent 中启用这套 Skill。

用户这次又说：

> 这一场我要写得慢一点，多留一点情绪铺垫。

本次明确要求优先于 Skill 的默认建议。Skill 不能以“你的写法要求”为理由拒绝用户的改变。

### 场景五：剧本完成后沉淀 Skill

用户：

> 总结这部剧里我反复保留的写法，做成以后可复用的 Skill。

Agent 先展示候选经验，而不是直接生成永久规则：

- 哪些冲突处理被用户多次保留；
- 哪些台词或叙述方式被用户主动修改回来；
- 哪些检查问题在多个场景中重复出现；
- 哪些内容只是本项目的特殊人物和情节。

用户选择要沉淀的部分后，系统生成一套带来源和适用范围的 Skill。例如：

> 来源于当前项目的修改记录，适合现实题材人物冲突；只作为参考，不代表所有题材都适用。

本项目的故事事实不会被误当成通用写法，整部剧也不会被原样复制成 Skill。

### 场景六：安装已有的写法 Skill

用户：

> 我有一套自己的写法资料，安装它。短剧项目可以使用，但小说项目不要自动使用。

系统在安装前展示名称、来源、资源、适用范围和可能的风险。安装后，Skill 可以被短剧 Agent 按需加载，但不能获得新的文件权限，也不能替用户提交正式文件。

用户以后可以说：

> 这次先不要参考我的写法，按当前项目的需要来。

Agent 应当临时停用该 Skill，而不是强行套用。

### 场景七：灵感库的使用

用户：

> 把刚才这个人物关系存到灵感库，先不要放进当前剧本。

之后用户可以说：

> 从灵感库里找三个适合现在这部剧的冲突点。

Agent 找出候选内容并说明来源。用户选中后，可以：

- 继续留在灵感库；
- 作为当前任务的参考；
- 加入当前项目的草稿；
- 提炼成 Skill 的一个案例。

灵感默认不是项目事实，也不会自动进入所有对话上下文。

### 场景八：创建自己的短剧 Agent 或小说 Agent

用户：

> 我想创建一个小说 Agent，重点帮我整理世界观、人物关系和章节结构，不要主动替我决定剧情。

创造模式通过对话确认：

- Agent 服务的领域；
- 它需要理解哪些项目对象；
- 要挂载哪些 Skill；
- 哪些任务可以自动完成；
- 哪些创作分叉必须询问用户；
- 输出是草稿、分析还是正式文件。

最后生成的是一份可组合的 Agent 配置，而不是一段孤立的超级 Prompt。

## 4. 四类能力如何组合

### 项目

保存当前故事的正式事实，例如人物、设定、大纲、正文、连续性和版本。项目不保存“所有用户偏好”，也不自动把参考资料变成事实。

### Skill

保存可复用的知识和方法，例如：

- 写法偏好；
- 创作工作流；
- 某类题材知识；
- 审查问题；
- 用户选定的案例。

Skill 可以附加到用户、项目或某个 Agent，但作用范围应清楚可见。

### 灵感

保存尚未决定是否进入项目的内容。它是素材仓库，不是正式项目，也不是自动生效的 Skill。

### Agent

保存“如何工作”的组合：

```text
领域：短剧 / 小说
项目对象：场、集、章节、人物、世界观等
工具：读取、草稿、校验、版本、交付
Skill：用户写法、领域知识、审查视角
交互偏好：何时自动做、何时询问
```

领域 Profile 决定它能理解和校验什么；Skill 决定它可以参考什么；用户决定最终创作方向。

## 5. 文件和目录应该怎么处理

用户可以自由组织可见文件。Agent 先识别，再使用，不要求所有项目都遵循同一套文件夹。

系统需要维护一份轻量的项目识别信息，回答这些问题：

- 哪个文件是当前项目的正式正文；
- 哪些文件是人物、设定和大纲；
- 哪些内容只是参考资料；
- 哪些模块启用或停用；
- 一个逻辑对象当前对应哪个实际路径。

这份识别信息不是让用户配置复杂后台，而是让系统记住用户已经确认过的关系。

建议分三类：

- **核心能力**：项目绑定、版本、草稿/正式文件、安全范围，不能关闭；
- **可选模块**：人物库、全剧大纲、时间线、世界观、场景库等，用户可以启用或停用；
- **普通资料**：用户自己创建的笔记和目录，Agent 可以读取，但只有用户确认后才登记为项目对象。

标准短剧目录可以保留为“新建项目模板”，但不应成为所有项目的硬性前提。

## 6. 用户权限和系统保护

应该尽量放大的，是用户的创作权：

- 自己定题材、风格、人物和结局；
- 自己选择工作流；
- 自己安装和停用 Skill；
- 自己组合项目模块；
- 自己决定是否接受建议和提交正式文件。

不能无限放大的，是 Agent 的系统权限：

- 不能访问项目外路径；
- 不能因为 Skill 要求而创建、删除或移动大量文件；
- 不能绕过正式文件写入和版本记录；
- 不能绕过版本和恢复机制；
- 不能未经确认执行不可逆删除或覆盖。

这两类权限必须分开，否则“创作自由”会变成“项目不可控”。

## 7. 当前架构的适配判断

当前内核已经具备一部分基础：

- 项目 Session 绑定和项目内读写限制；
- 短剧领域工具、正式文件写入和版本记录；
- A 类格式校验与版本恢复；
- Skill 发现、按需加载和资源隔离；
- 参考文件与正式项目事实的区分。

当前的主要限制是：

- 项目创建仍然倾向于一次性生成固定目录；
- 布局识别主要是固定的两套路径；
- 部分领域工具把固定路径和固定前置文件当作前提；
- 用户还不能通过自然对话完成 Skill 的创建、安装、更新和卸载；
- 灵感库和用户自定义 Agent 还没有形成完整产品闭环。

因此，这不是短剧领域能力要不要保留的问题，而是需要把“固定项目模板”升级为“可识别、可配置的项目工作区”。

## 8. 实现时必须守住的边界

### 可以开放

- 可见目录和文件名；
- 可选项目模块；
- 用户自己的 Skill；
- Agent 的领域、工具和 Skill 组合；
- 用户选择的写作顺序和审美方向。

### 不应交给 Skill 或 Agent 自行决定

- 项目外访问权限；
- 系统私有状态的位置和格式；
- 正式版本是否被覆盖；
- 用户明确否定的创作方向；
- 把某种写法升级成短剧的唯一标准。

### 必须向用户说明

- 当前使用了哪些 Skill；
- 哪些建议来自 Skill，哪些是 Agent 的推断；
- 哪些文件被识别为项目对象；
- 哪些内容只是草稿；
- 提交、删除、恢复等不可逆操作的结果。

## 9. 验收标准

从用户角度，至少应该能完成以下体验：

1. 用户只描述创作意图，Agent 能先观察项目并开始工作，不要求用户指挥文件操作。
2. 用户可以在不遵循标准目录的工作区中继续创作，确认后 Agent 能记住文件用途。
3. 用户可以选择不用全剧大纲或其他可选模块，Agent 不因模板缺失而无条件阻断。
4. 用户可以安装、停用和指定范围使用自己的写法 Skill。
5. 用户可以从完成项目中选择性提炼 Skill，且项目事实不会被原样复制成规则。
6. 用户可以把对话内容保存到灵感库，并决定何时送入项目或 Skill。
7. 用户可以通过创造模式组合一个短剧 Agent 或小说 Agent，但不能配置出越权文件权限。
8. 用户明确的创作选择优先于 Skill 建议；系统硬安全规则仍然有效。
9. 普通创作过程不要求用户理解 Artifact、revision 或工具名称；这些信息在需要时可查看。

## 10. 非目标

本设计暂不承诺：

- 自动判断某种写法一定正确；
- 自动把全部作品总结为稳定文风；
- 让 Skill 直接编写或管理系统权限；
- 通过一个超级 Prompt 覆盖短剧、小说等所有领域；
- 用独立后台取代自然语言作为 Skill 和 Agent 的主要入口。

## 11. 最终产品判断

短剧 Agent 的专业性不应体现在“要求用户按固定步骤操作”，而应体现在：

- 它能理解短剧创作中的对象和问题；
- 它能在用户自己的工作区中找到并维护上下文；
- 它能把机械校验和创作建议分开；
- 它能记住用户确认过的选择；
- 它能把一次项目经验沉淀为可选能力；
- 它不会替用户决定作品的味道。

因此，目标体验是：

> **用户负责创作和拍板，Agent 负责理解和执行，项目负责承载，Skill 负责提供参考，系统负责保护完整性。**
