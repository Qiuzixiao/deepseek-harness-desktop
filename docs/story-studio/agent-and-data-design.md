# Story Studio Agent 与项目数据设计

## 1. 设计目标

Agent 必须同时适应两种用户：

- 只知道一个故事点子的创作者，希望 Agent 帮助补足定位、人物和结构；
- 已经有专业需求、对标材料、集数、受众和交付目标的职业编剧，希望 Agent 直接执行。

因此不能把固定问卷或严格阶段门禁当成入口。Agent 的核心行为是：识别当前信息是否足以完成“本轮交付”，只解决会改变结果方向的冲突，把普通细节做成可审阅草案。

## 2. 单 Preset、多 Skill

首个 MVP 只交付一个 `Story Studio` Preset，原因如下：

- 短剧和小说共享需求整理、项目文件、参考拆解、人物、世界、研究和审校能力；
- 两者需要的官方工具面相同，没有必要复制完整 Agent composition；
- Skill 比 Preset 更适合承载可组合的专业方法；
- 一个会话可能从故事开发切换到短剧改编或小说扩写，单 Preset 不要求重建会话工具上下文。

Preset 只定义稳定身份和能力边界。它不能把某一种样例目录、固定集数或“每次必须先问七个问题”写死在 persona 中。

## 3. 需求完整度判断

Agent 先把输入整理为五组信息：

1. **作品形态**：短剧、小说，或尚未决定；
2. **创作核心**：一句话梗概、核心冲突、角色关系、卖点；
3. **结构约束**：季/卷、集/章数量、单集/单章长度、时间范围；
4. **市场约束**：平台、受众、题材、调性、尺度、对标；
5. **本轮交付**：选题整理、人物、故事 Bible、大纲、分集、正文、审校或改写。

然后按影响分级：

| 等级 | 处理方式 | 示例 |
| --- | --- | --- |
| 冲突/阻塞 | 必须询问 | 同时要求 35 集和 50 集；第一季边界决定主线结局 |
| 高影响缺失 | 集中询问或给推荐选项 | 尚未决定短剧还是小说，但本轮要求完整结构 |
| 普通缺失 | 使用明确假设并写入 brief | 配角姓名、具体乡镇名、某场景的小道具 |
| 可后置 | 不阻塞当前工作 | 海报文案、最终投稿格式、第二季具体集数 |

提问规则：

- 每轮最多集中提出三个高影响问题；
- 每个问题给出推荐默认项及其影响；
- 不重复询问用户已经明确的事实；
- 专业输入足够完成本轮交付时直接执行；
- 用户暂不决定时，用推荐假设推进并标记为 `待确认`；
- 事实与假设必须进入 `项目说明.md`，不能只留在聊天记录；`brief.md` 只作为旧项目兼容读取路径。

## 4. Skills 职责

### 4.1 `story-intake`

负责解析输入、发现冲突、判断本轮交付、组织问题和写入 brief。它不负责生成完整人物或正文，避免需求判断与创作结果混在一个不可复核步骤里。梳理核心卖点/核心冲突时，可用 grep 按关键词检索 `灵感速记/灵感速记.md`，命中则评估是否并入 brief，未命中不阻塞。

### 4.2 `story-project`

负责创建和检查项目结构、维护 `项目配置.yml`、汇总状态、定位产物。可携带确定性脚本：

- `init`：建立目录和最小文件；
- `validate`：验证 schema、路径、编号和必需引用；
- `status`：从文件推导阶段、完成度、风险和下一步；
- `migrate`：未来 schemaVersion 升级时显式迁移。

这些脚本只操作当前工作区项目，不写入 DSH home 或其他作品。

### 4.3 `short-drama-writing`

负责短剧专用方法：季边界、集长、开场钩子、单集目标、冲突升级、反转、付费卡点、下集钩子、场次和口语化台词。它读取公共 Bible 和人物文件，但将分集纲与分集正文写入短剧目录。构思反转、钩子或卡点前，可用 grep 按当前场景关键词检索 `灵感速记/灵感速记.md`，命中则评估是否采用，未命中直接继续。

### 4.4 `novel-writing`

负责小说专用方法：卷章结构、视角、章节目标、情节线、人物演化、伏笔、章节摘要和长程连续性。它不能默认批量生成大量未审阅正文；批量规模由用户要求和 checkpoint/审校能力共同限制。构思人设或情节转折前，可用 grep 按关键词检索 `灵感速记/灵感速记.md`，命中则评估是否采用，未命中直接继续。

### 4.5 `reference-analysis`

负责材料导入后的来源登记、结构拆解、角色功能、爽感/悬念节奏、风格特征和可迁移方法。输出必须区分：

- 原材料事实或原文摘录；
- Agent 的分析结论；
- 可以应用到新作品的抽象方法；
- 不得直接复用的具体表达、角色或独特情节组合。

### 4.6 `story-review`

负责一致性和交付审校，至少检查：

- 人物欲望、能力、关系和行为是否冲突；
- 时间线、年龄、地点、道具和时代事实是否冲突；
- 大纲目标是否在正文出现；
- 短剧开场、反转、卡点和结尾钩子是否成立；
- 小说视角、章节目标、伏笔和人物演化是否连贯；
- 台词、叙述和格式是否符合项目风格；
- 修改建议是否会破坏已确认设定。

审校默认先产生报告，不直接覆盖正文。用户或主 Agent 选择修订项后再写入。

## 5. 动态 Workflow 配方

DSH Workflow 当前执行模型生成的编排脚本，不提供保存工作流产品。Story Studio 不再建一个平行工作流系统，而是在 Skills 中维护以下配方：

### 5.1 立项配方

主 Agent 整理 brief；人物、世界/时代研究和结构方案可并行；主 Agent 汇总冲突并形成 Bible 和主纲。

### 5.2 分集/分章配方

先由主 Agent固定主线边界，再把不重叠的集/章范围分给子智能体。子智能体只能写分配范围，主 Agent 负责跨范围连续性和编号检查。

### 5.3 审校配方

结构、人物一致性、时代事实和语言风格可并行审查；最终报告按严重度合并、去重，并指出证据文件。

### 5.4 参考拆解配方

材料解析、结构抽取、人物功能、市场/时代研究可并行；最终由主 Agent 区分原作事实与可迁移方法。

Workflow 使用限制：

- 小任务直接由主 Agent 完成，不为“显得智能”而启动子智能体；
- 子智能体任务必须有明确输入文件、输出文件和禁止修改范围；
- 并行任务不得写同一个文件；
- 主 Agent 在写入前检查子结果是否互相矛盾；
- 任务中断后以落盘文件和 DSH session 为恢复依据，不声称 Workflow 可以跨进程续跑。

## 6. 项目文件合同

建议目录：

```text
<作品目录>/
  项目配置.yml
  项目说明.md
  故事设定/
    故事前提.md
    世界规则.md
    时间线.md
    写作风格.md
    人物/
      <角色-id>.md
  参考资料/
    参考资料索引.md
    原始资料/
    分析/
  故事大纲/
    季纲/
      第01季.md
    分集大纲/
      第01季-第01集.md
    卷纲/
      第01卷.md
    章节大纲/
      第01卷-第001章.md
  正文草稿/
    短剧/
      第01季-第01集.md
    小说/
      第01卷-第001章.md
  审校记录/
    修订/
  灵感速记/
    灵感速记.md
  导出/
  .qnovel/
    缓存/
    索引/
```

已有旧项目仍可使用 `story.yml`、`brief.md`、`bible/`、`references/`、`outline/`、`drafts/` 和 `reviews/` 读取；新项目不再写入这些英文路径，也不自动重命名旧项目。

短剧只要求 seasons/scripts，小说只要求 volumes/chapters。公共 Bible、references 和 reviews 不复制。

### 6.1 `项目配置.yml`

最小字段建议：

```yaml
schemaVersion: 1
id: 1998-father-and-son
title: 1998满仓父子局
medium: short-drama
language: zh-CN
status: development
currentDeliverable: season-1-outline
format:
  seasons: 1
  episodesPerSeason: 50
  episodeDurationMinutes: 2
audience:
  primary: 下沉市场男频用户
genres:
  - 重生
  - 年代创业
  - 父子
```

结构化字段只保存稳定事实和状态；长段创作内容写入 Markdown。字段扩展必须保持未知字段可保留，schema 升级通过显式 `schemaVersion` 和迁移完成。

### 6.2 `项目说明.md`

必须包含：

- 原始需求摘要；
- 已确认事实；
- Agent 使用的假设；
- 待确认问题；
- 用户明确禁止或必须保留的内容；
- 本轮交付物；
- 参考材料清单和使用边界。

### 6.3 人物文件

一名主要人物一个文件，避免多人并行时争写 `characters.md`。人物文件至少包含身份、目标、欲望、恐惧、能力/限制、关系、秘密、弧光、当前状态和证据来源。

### 6.4 参考索引

`参考资料/参考资料索引.md` 记录原文件名、外部路径或项目副本、文件类型、导入时间、使用许可说明、解析状态和分析文件。分析引用必须尽量包含页码、章节、场次或可定位片段。

### 6.5 灵感速记

`灵感速记/灵感速记.md` 是单一追加型日志文件，不采用一条一文件的模式——该模式只为避免多个子智能体并行写入同一文件冲突，而灵感速记是单一用户顺序追加的动作，不存在这个问题。

写入触发方式：`/idea` Skill 手势或自然语言（如“记一下这个灵感”），两者等效。每条追加使用二级标题，包含日期时间和若干关键词/标签，便于后续按关键词 grep 命中，标题下为 1-2 行正文：

```markdown
## 2026-08-19 22:10 反转结构 父子关系
儿子发现"死去"的父亲其实用假身份活着，一直在暗中帮衬家里生意。
```

读取方式遵循第 8 节的按需搜索原则：不在每轮创作开始时整份读取，而是由 `story-intake`、`short-drama-writing`、`novel-writing` 在构思核心卖点、反转、钩子、人设或情节转折等具体时刻，用 fs search 的 grep 按当前场景关键词检索该文件；命中则评估是否采用，未命中不阻塞、不追问。

### 6.6 生成状态

`.story-studio/` 只存缓存、索引、检索数据库和可重建状态。删除该目录不能导致作品正文、Bible、大纲、审校和决策永久丢失。

## 7. 三种历史的职责

| 历史 | 保存什么 | 不负责什么 |
| --- | --- | --- |
| DSH Session | 用户意图、Agent 推理过程、问题、工具调用和决策过程 | 不是作品正文事实源 |
| Git | 人类认可的长期项目版本和协作历史 | 不需要记录每一个 Agent tool step |
| Checkpoint | Agent 修改前的短期可恢复状态 | 不替代 Git commit 和正式版本 |

## 8. 上下文策略

MVP 使用分层文件和按需搜索，不默认引入 RAG：

1. 每次读取 story、brief 和本轮直接相关的 Bible；
2. 读取主纲、当前集/章细纲和最近正文；
3. 用 fs search 检索人物、地点、物品、伏笔和灵感速记；
4. 将已完成集/章维护为短摘要；
5. 只有真实基准证明召回不足时，启用一个本地知识插件；
6. RAG 索引是派生物，结果必须回指项目原文件。

禁止把完整世界书、全部章节和全部参考原文无差别注入每次模型请求。
