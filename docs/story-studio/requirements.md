# QNovel Beta 产品需求文档

状态：**方案评审稿**  
目标用户：内部短剧编剧、小说编剧、编导和内容负责人

## Problem Statement

内部创作者输入的信息完整度差异很大。一部分人只提供故事梗概，需要帮助判断题材、受众、人物和结构；另一部分人已经带着集数、平台、对标剧本和明确交付目标工作，不希望再经历固定问卷。

通用聊天 Agent 可以生成文本，但缺少稳定的作品目录、阶段状态、长篇一致性、参考材料引用、文件审阅、修改回退和专业交付。单独建设一套新的 Agent Runtime、文件编辑器、Git UI 和知识库会重复 DSH 与社区生态已有能力，也会显著增加与官方上游同步的成本。

产品需要把 DSH Desktop 组合成面向编剧的内部工作台：输入足够时直接执行，信息模糊或冲突时只询问高影响问题；所有作品内容落到可读、可编辑、可版本管理的本地项目文件中。

## Solution

QNovel 以专用 DSH Profile 交付，组合官方 Workspace、Session、Agent、Skills、Subagents、Workflow、文件、附件、Web 和 Client Slots，并引入经过审核、固定版本的第三方插件解决文档导入、文件编辑、Git 和修改回退。

产品提供一个 Story Studio Preset 和一组领域 Skills。Agent 将需求、假设和待决问题写入 `项目说明.md`，按作品形态生成公共故事设定、短剧季/集文件或小说卷/章文件，并在写入后执行一致性审校。工作区 Markdown/YAML 是作品事实源，Git 保存长期版本，Checkpoint 保护 Agent 操作，DSH Session 保存创作过程。

## User Stories

1. 作为只拥有一句故事想法的编剧，我希望 Agent 帮我识别真正缺失的关键决策，以便快速形成可讨论的选题和人物方案。
2. 作为职业编剧，我希望已经明确的题材、受众、集数和风格被直接采用，以便不被重复问卷打断。
3. 作为编剧，我希望相互冲突的集数、季范围或交付要求被明确指出，以便在错误结构扩散前做决定。
4. 作为编剧，我希望普通细节先使用可审阅假设，以便在信息不完整时仍能推进工作。
5. 作为编导，我希望看到哪些内容已确认、哪些是 Agent 假设、哪些仍待决定，以便快速评审创作基础。
6. 作为短剧编剧，我希望生成季纲、分集纲、分场正文、钩子、反转和卡点，以便按短剧生产方式工作。
7. 作为小说编剧，我希望生成卷纲、章纲、章节正文、人物演化和伏笔记录，以便管理长篇连载。
8. 作为跨媒介创作者，我希望同一个作品可以先做故事开发，再选择短剧或小说方向，以便不重复建立项目资料。
9. 作为编剧，我希望一名主要人物拥有独立人物档案，以便多人或多个 Agent 并行时减少文件冲突。
10. 作为编导，我希望人物、时间线、地点、道具和时代事实能够被审校，以便在交付前发现连续性错误。
11. 作为编剧，我希望审校先输出证据和建议而不是直接覆盖正文，以便保留创作判断权。
12. 作为编剧，我希望能导入 DOCX 和文本层 PDF 参考资料，以便使用已有剧本；Excel、PPT 和扫描 PDF 的完整生产不属于当前 MVP。
13. 作为编导，我希望参考分析标记来源文件和可定位位置，以便复核结论而不是信任无来源摘要。
14. 作为内容负责人，我希望对标分析只抽象结构、节奏和角色功能，以便降低复写原作表达的风险。
15. 作为编剧，我希望所有重要产出保存到项目目录，以便在外部编辑器中继续工作并避免只存在聊天记录。
16. 作为编剧，我希望能在应用内浏览和编辑项目 Markdown 文件，以便减少在多个工具间切换。
17. 作为编剧，我希望看到 Agent 修改前后的 diff，以便快速判断是否接受修订。
18. 作为编剧，我希望 Agent 修改可以按 checkpoint 回退，以便大胆尝试而不破坏已有版本。
19. 作为维护者，我希望 checkpoint 不移动 Git HEAD 或破坏暂存区，以便短期撤销与正式版本控制互不干扰。
20. 作为内容负责人，我希望 Git 保存人工认可的长期版本，以便追踪里程碑和正式交付。
21. 作为编剧，我希望重启应用后继续同一作品和会话，以便长周期创作不依赖一次运行。
22. 作为编剧，我希望 Agent 只加载本轮相关设定和正文，以便长篇项目不会因全量上下文而失控。
23. 作为编剧，我希望能检索早期人物事实和伏笔，以便续写时保持前后一致。
24. 作为维护者，我希望只有真实基准证明需要时才引入 RAG，以便控制应用体积、模型下载和原生依赖。
25. 作为编剧，我希望最终作品以清晰的 Markdown/YAML 项目文件交付；专业 DOCX/PDF 排版导出留给后续阶段。
26. 作为维护者，我希望第三方插件被锁定到精确版本和校验和，以便产品升级可复现。
27. 作为维护者，我希望第三方插件分别通过安装、调用、重启和卸载测试，以便某个插件失败时可独立排除。
28. 作为维护者，我希望产品同时验证 Desktop compatibility 和 advanced 模式，以便第三方 UI 不破坏桌面壳。
29. 作为维护者，我希望 macOS 和 Windows 安装包验证 native module ABI，以便开发环境可用不被误判为发行可用。
30. 作为维护者，我希望 Story Studio 不修改官方 Harness 子模块，以便继续同步官方能力和安全修复。
31. 作为维护者，我希望通用 DSH Desktop 与 Story Studio 产品资源分层，以便桌面壳不被编剧领域逻辑污染。
32. 作为内部用户，我希望产品不要求账号、支付或公共云服务，以便在内部环境直接使用。
33. 作为内部用户，我希望插件不会把剧本和参考材料上传到未声明服务，以便保护未公开内容。
34. 作为维护者，我希望插件市场只负责发现候选，以便未经审核的代码不会自动进入生产 Profile。
35. 作为产品负责人，我希望项目状态、风险和下一步来自作品文件事实，以便界面状态不会与实际产物分离。

## Implementation Decisions

- 产品是专用 Profile 和发行组合，不是单一大型插件。
- 使用一个 Story Studio Preset，通过多个 Skills 区分专业工作。
- 需求澄清采用影响分级，一次最多询问三个高影响问题。
- 作品 Markdown/YAML 是唯一事实源；隐藏数据库和向量索引必须可重建。
- DSH Session、Git 和 Checkpoint 分别保存过程、长期版本和短期恢复点。
- 使用官方 Workspace、Session、fs、attachments、presets、skills、subagents、workflow、jobs、questions、web 和 Client Slots。
- 文档导入、文件编辑/Git 和回退先评估现有插件，未通过当前 DSH 与桌面发行门禁前不预装。
- 项目合同解析、验证、迁移和状态推导设计为可独立测试的深模块。
- 项目工作台使用产品 Client Slot 实现名称创建与作品选择，并复用 Better Sidebar 的文件树、编辑器和预览。
- 首次启动必须选择全局作品目录；Settings 可以更改该目录；新建作品只输入名称并写入当前配置根目录，不自动搬迁已有作品。
- 产品可见名是 `QNovel Beta`；QNovel 替换左侧官方 Logo 位置，右上角重复“新建作品”入口删除，官方 Conversation、Session、Workspace 和当前 Workbench 保留。
- 新建作品统一使用中文物理路径和文件名；旧的 `story.yml`、`brief.md`、`bible/`、`outline/`、`drafts/` 仅兼容读取，不自动重命名。
- RAG 必须经过统一中文语料基准，只选择一个实现进入产品 Profile。
- 第三方依赖锁记录版本/commit、来源、hash、许可证、权限、原生依赖和兼容证据。

## Testing Decisions

- 测试用户可观察行为，不断言模型逐字输出或 UI 内部组件结构。
- `story-project` 的初始化、验证、状态和迁移使用真实临时文件测试。
- 模糊需求、专业需求、冲突需求、参考拆解和长篇续写建立固定场景回归。
- 第三方插件先单独验证，再验证 Rich File Reader、文件/Git UI 和 Checkpoint 的组合。
- 文档输入仅以真实 DOCX 和文本层 PDF 为当前验收样例；不验收 XLSX、PPTX 和扫描 PDF 生产流程。
- Checkpoint 测试覆盖 tracked、untracked、staged、ignored、Git 与非 Git 项目。
- Client 插件验证普通 Web、Desktop compatibility、Desktop advanced 和最小窗口布局。
- 涉及原生依赖的插件必须在 macOS 与 Windows packaged app 中验证。
- RAG 以 Recall@K、错误引用、来源定位、索引时间、资源和冷启动比较候选。
- 每个实现切片执行仓库 layout、typecheck、unit、build 和完整 check 门禁。

## Out of Scope

- 会员、支付、套餐、用量计费和商业化后台；
- 公共云项目存储、多人实时协作和组织权限；
- 面向外部用户开放的插件市场安装器；
- 自研模型推理或本地大模型；
- 重写 DSH Agent Runtime、Session、Workspace、文件系统或 Web Client；
- 在 MVP 中强制安装本地 embedding/RAG；
- 自动发布到短剧或小说平台；
- 用一个第三方小说插件的数据协议定义整个 Story Studio 产品；
- 专业 DOCX/PDF 排版导出；
- Excel、PPT 和扫描 PDF 的完整生产流程；
- 安装包发布（当前阶段只运行本地开发版）。

## Further Notes

- 用户现有 `script-studio` Preset 是能力回归夹具，不是产品需求或最终架构。
- 当前第三方候选多数只声明兼容 DSH `rc.6`，产品基线为 `0.1.1-rc.1`；因此仍需独立 runtime smoke。
- 产品实现应按纵向交付切片推进：先跑通创作流程，再增加项目状态、导出和长篇知识能力。
- 详细技术方案、插件证据和验收标准分别见本目录其他文档。
