# 短剧 Agent 能力组合总实施文档

状态：提案

> **实现状态说明（2026-09）**：本文整体是历史能力提案，不是当前运行契约。当前没有 `write_episode`、`validate_episode`、`diagnose_episode`、草稿/提交、领域状态或固定布局；普通文件通过通用文件工具直接处理。当前实现见 `dsh-short-drama/README.md`。

本文统筹以下四份 PRD：

- [从已完成项目沉淀可复用 Skill](prd/short-drama-skill-extraction.md)
- [用户 Skill 安装与复用](prd/skill-installation-and-reuse.md)
- [首页灵感库](prd/inspiration-library.md)
- [创造模式与自定义 Agent](prd/agent-creator-mode.md)

## 1. 总体结论

四个需求可以实现，但不能把它们继续做成四套互相独立的 Prompt 功能。

它们应该共享一套基础关系：

```text
创作项目       保存当前故事的正式内容和版本
灵感库         保存尚未决定是否进入项目的素材
Skill          保存可复用的写法、工作流、知识和审查视角
Agent          组合领域能力、Skill 和交互偏好
Harness        保护权限、会话、版本和安全路径
```

用户面对的是自然对话；文件登记、Skill 加载、版本记录和工具调用由系统在后台完成。用户可以修改创作方向和工作方式，但不能通过 Skill 或 Agent 配置绕过系统安全。

## 2. 目标用户体验

### 新项目

用户：

> 我想写一部都市悬疑短剧，从一个女人发现丈夫在撒谎开始。

Agent 先观察项目是否为空，再给出创作方向或直接写开场。用户不需要先选择“创建人物文件”或“创建大纲文件”。项目内部可以保留必要状态，用户可见的目录和创作顺序不应成为前置负担。

### 已有工作区

用户打开自己已经整理好的目录：

```text
人物笔记.md
故事梗概.md
正文/第一集.md
参考/采访记录.pdf
```

用户：

> 接着上一集写，女主暂时不能揭穿丈夫。

Agent 先读取并识别文件，必要时只请求一次确认，然后沿用用户的组织方式。系统不要求把文件搬到固定目录。

### 项目完成后

用户：

> 把我在这部剧里反复坚持的写法整理成 Skill，但不要带入具体故事。

Agent 展示带证据的候选经验，用户选择后发布 Skill。原项目不被修改。

### 跨项目复用

用户：

> 安装我的写法 Skill，短剧可用，小说不要自动用。

系统验证后安装到用户作用域。用户以后可以在某个项目或某个 Agent 中启用、停用或替换它。

### 灵感进入创作

用户：

> 从灵感库找三个适合第二集的冲突点，先比较，不要写进正文。

Agent 只返回候选。用户说“采用第二个，放进草稿”，系统才把它送入当前草稿；正式提交仍需用户决定。

### 创建 Agent

用户：

> 做一个重对白的短剧 Agent，重大反转必须问我；再做一个只整理世界观和章节结构的小说 Agent。

创造模式分别生成两个 Agent 配置。它们共享底层权限和版本能力，但使用不同的领域对象和校验器。

## 3. 分层设计

### 3.1 用户工作区

用户可以自由放置文件、命名目录和保留自己的笔记。Agent 通过项目内读取和搜索理解内容，不能访问项目外路径。

### 3.2 项目识别层

项目识别层记录“某个文件当前承担什么作用”，例如某文件是人物设定、分集大纲或正式正文。它不要求物理目录统一，也不把普通笔记强行登记为正式 Artifact。

识别关系应支持：

- 自动识别后的用户确认；
- 一个逻辑对象对应一个实际文件或一组文件；
- 可选对象未启用时不触发无条件前置错误；
- 文件移动和重命名产生可追踪记录；
- 识别不确定时保留原文件，不擅自搬运或覆盖。

项目仍需保留少量内部状态，用于 Session 绑定、草稿、revision 和恢复；这些状态不应由 Skill 自定义。

### 3.3 领域 Profile

领域 Profile 定义 Agent 能理解的对象和客观能力：

- 短剧：集、场、人物、连续性、时长、卡点、交付；
- 小说：卷、章、人物弧线、世界观、叙事视角；
- 其他领域可在相同 Harness 上增加自己的 Profile。

Profile 只负责领域基础设施，不规定统一审美。写法和风格由用户和 Skill 决定。

### 3.4 Skill 知识层

Skill 有三种主要来源：系统随附、用户安装、用户从项目提炼。Skill 可以提供写法、流程、领域知识、问题清单和审查视角。

Skill 必须带有：来源、版本、适用范围、作用域和启用状态。它不能声明额外文件权限、执行任意代码或改变正式提交规则。

### 3.5 灵感库

灵感库保存尚未成为项目事实的素材。它可以被送入当前任务、项目草稿或 Skill 候选，但每种转换都要留下来源和状态。

### 3.6 Agent 配置层

Agent 是一个可解释的组合：

```text
领域 Profile
+ 领域能力
+ Skill 引用
+ 用户交互偏好
+ 适用范围
+ 版本和状态
```

Agent 配置不能增加 Harness 的系统权限，只能决定如何使用已授权的领域能力和 Skill。

## 4. 关键数据关系

```text
项目
 ├─ 项目识别关系 ──→ 用户工作区文件
 ├─ 正式版本 / 草稿
 └─ 项目范围的灵感和 Skill 引用

用户
 ├─ 用户范围的灵感
 ├─ 用户安装的 Skill
 └─ 用户创建的 Agent

Agent
 ├─ 一个领域 Profile
 ├─ 多个 Skill 引用
 └─ 一个作用域和交互策略
```

重要区分：

- 灵感不是项目事实；
- 项目事实不是 Skill 规则；
- Skill 不是工具权限；
- Agent 配置不是任意代码；
- 草稿不是正式版本。

## 5. 统一交互规则

### Agent 自动处理

- 读取当前项目和相关文件；
- 识别文件用途并复用已确认关系；
- 选择匹配的 Skill；
- 保存草稿、读回内容和运行机械校验；
- 修复普通格式问题；
- 整理灵感和生成候选方案；
- 展示来源、风险和版本信息。

### Agent 必须询问

- 多个创作方向都会改变故事走向；
- 用户明确改变人物底层动机或结局；
- 文件用途无法判断且会影响写入位置；
- 用户要把内容登记为项目事实或发布为 Skill；
- 提交、删除、恢复等不可逆操作；
- 需要选择用户作用域还是项目作用域。

### 系统始终保护

- 项目作用域和路径安全；
- 私有状态和版本记录；
- 草稿/正式文件边界；
- 领域工具的校验和原子写入；
- Skill 资源隔离；
- 用户明确选择优先于 Skill 建议。

## 6. 实施顺序

### 阶段一：项目开放工作区和识别层

目标是让 Agent 不再依赖一套不可变的可见目录。

主要结果：

- 新项目只创建必要的内部状态和用户选择的初始模板；
- 读取和搜索先观察工作区，再识别文件用途；
- 用户确认的文件关系可持久化；
- 短剧领域工具通过逻辑对象找到文件，而不是在调用方写死路径；
- 已有标准短剧项目继续可读，旧布局作为迁移输入而非用户体验限制。

完成这一阶段后，用户可以像使用通用工作区 Agent 一样开始创作。

### 阶段二：Skill 安装、启用和作用域

主要结果：

- 支持自然语言导入本地 Skill；
- 安装前检查和预览；
- 用户/项目作用域隔离；
- 启用、停用、更新、卸载和版本恢复；
- Skill 资源安全读取，不执行任意代码。

完成这一阶段后，用户可以真正使用自己的写法 Skill。

### 阶段三：项目到 Skill 的提炼

主要结果：

- 读取版本差异和用户确认记录；
- 生成带证据的候选经验；
- 区分通用写法与项目事实；
- 用户选择、编辑和发布 Skill；
- 原项目和正式版本不受影响。

这一阶段依赖版本记录和 Skill 生命周期，但不依赖灵感库界面。

### 阶段四：首页灵感库

主要结果：

- 从对话保存灵感；
- 按类型、标签、来源和项目搜索；
- 作为参考、送入草稿、登记为事实或转为 Skill 候选；
- 保留来源和状态；
- 不自动污染项目上下文。

### 阶段五：创造模式和 Agent 配置

主要结果：

- 对话式创建短剧 Agent、小说 Agent；
- 选择领域 Profile、能力、Skill 和交互偏好；
- 配置预览、示例任务测试、保存和版本管理；
- 应用到项目或设为默认；
- 限制为声明式配置，不允许自定义任意权限或代码。

这一阶段依赖稳定的 Skill 注册和领域 Profile。

### 阶段六：跨能力联动和质量回归

主要结果：

- 灵感可以进入项目草稿或成为 Skill 候选；
- 项目提炼的 Skill 可以挂载到自定义 Agent；
- Agent 使用记录包含 Skill 和配置版本；
- 短剧、小说等 Profile 共用安全、会话和版本基础设施；
- 完成端到端自然语言场景回归。

## 7. 当前架构适配与需要升级的地方

当前短剧内核已有可复用基础：项目 Session 绑定、项目内读写限制、领域草稿、A 类校验、正式提交、版本恢复、Skill 发现和资源隔离。

需要升级的核心位置不是 Prompt，而是项目识别层：

- 现有固定布局需要变成可识别的逻辑对象映射；
- 可选模块不能继续被当成永远存在的前置文件；
- Agent 应先探索工作区，再选择领域能力；
- Skill 生命周期需要从“能读取”扩展到“可安装、可停用、可版本化”；
- 版本记录需要能支撑项目经验提炼；
- 灵感和 Agent 配置需要有独立存储和作用域。

## 8. 冲突风险和处理原则

| 风险 | 处理原则 |
| --- | --- |
| 用户目录与领域工具不一致 | 先识别并请求确认，保留逻辑对象与实际路径的对应关系 |
| 用户关闭某个模块 | 将其标记为未启用，不把缺失当作系统损坏 |
| Skill 与用户当前要求冲突 | 用户当前明确要求优先，Skill 只给建议 |
| 多个 Skill 给出不同流程 | 展示来源和取舍，不静默合并成新规则 |
| 灵感被误当成事实 | 默认独立保存，只有用户确认后才登记 |
| 项目事实被提炼成写法 | 生成候选时标注证据，要求用户选择 |
| Agent 配置试图扩大权限 | 由 Harness 权限层拒绝，配置保存失败 |
| 文件移动导致版本失联 | 迁移产生新版本，历史版本保留原路径和内容 |
| 自动操作误覆盖正式内容 | 先写草稿，正式写入需要领域提交和用户确认 |
| 自由度过高导致 Agent 不确定 | 让 Agent 说明识别结果和不确定性，只在影响决策时提问 |

## 9. 统一验收标准

从用户角度，系统至少要能完成：

1. 用户只说创作意图，Agent 就能探索工作区并开始工作，不要求用户指挥工具。
2. 用户可以使用任意组织方式的已有工作区，确认后 Agent 能记住文件用途。
3. 用户可以选择自己的创作顺序，缺少可选模块不会无条件阻断。
4. 用户可以安装、停用、更新和卸载自己的写法 Skill。
5. 用户可以从已完成项目中选择性提炼 Skill，且不复制具体故事事实。
6. 用户可以保存和搜索灵感，并决定灵感进入项目、草稿还是 Skill 候选。
7. 用户可以创建短剧 Agent 和小说 Agent，二者使用不同领域能力。
8. 用户的明确创作选择可以覆盖 Skill 和 Agent 默认建议。
9. 普通创作不要求用户理解文件路径、工具名称或版本参数。
10. 项目外访问、权限越界、错误覆盖和失败提交都被阻止。

## 10. 不建议采用的做法

- 继续增加一段更长的总 Prompt，试图解决目录、Skill、灵感和 Agent 的所有问题；
- 让 Skill 直接创建、删除或重命名系统项目目录；
- 把用户的整部剧原样打包成永久 Skill；
- 把灵感库自动注入每次对话；
- 用一个短剧 Prompt 加一个小说 Prompt 假装实现两个领域；
- 让创造模式生成任意权限或可执行代码；
- 把每次普通创作都变成文件确认和保存确认流程。

## 11. 最终判断

这四个需求应当作为一个“创作能力积累系统”建设，而不是四个孤立页面：

```text
用户创作项目
→ 积累灵感和修改经验
→ 选择性提炼 Skill
→ 安装或组合 Skill
→ 创建自己的 Agent
→ 在新项目中继续创作
```

用户始终负责作品方向和最终拍板；Agent 负责理解和执行；项目负责保存故事事实；Skill 负责提供可替换的参考；灵感库负责暂存尚未决定的素材；Harness 负责安全和完整性。
